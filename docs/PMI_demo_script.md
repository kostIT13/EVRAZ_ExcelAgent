# Сценарий демонстрации ПМИ — Excel-агент ЕВРАЗ

Сценарий превращает план прогона ПМИ ([`docs/PMI_run_plan.md`](PMI_run_plan.md)) в **30-минутную
живую демонстрацию**: 16 пунктов (Ф-1…Ф-13, К-1…К-3) сгруппированы в 7 «актов» по логике
«загрузил → спросил → проверил → построил → убедился в надёжности → получил метрики».

Ключевая идея: **всё долгое — уходит в фон в первые минуты**, всё эффектное — показывается вживую.

---

## 0. Подготовка (за 1 день и за 15 минут до демонстрации)

### За 1 день (T-1)

- [ ] Стенд развёрнут и «прогрет»: `docker compose up -d --build`; загрузить
      `data/data_proportional_prices.xlsx` + Faked-файл, прогнать 2–3 контрольных вопроса.
- [ ] Зафиксировать хэш файлов вопросов (`docs/request_examples.txt`) и эталонные значения.
- [ ] **Прогнать `python benchmark/run_all.py` заранее** и сохранить отчёт в
      `benchmark/results/` — это страховка для К-1…К-3, если живой прогон не уложится.
- [ ] Снять «запасные» скриншоты по каждому пункту Ф-1…Ф-13 (папка `frontend/screenshots/pmi/`).
- [ ] Проверить, что `/trace`, `/metrics`, история диалога содержат записи от прогрева.
- [ ] Подготовить второй браузер-профиль/инкогнито с уже открытой пустой сессией чата.

### За 15 минут (T-0)

- [ ] Открыть вкладки: `http://localhost:8080` (чат), `/docs`, `/trace`, `/metrics`.
- [ ] Открыть терминал в папке проекта (для команд `pytest`, `benchmark`).
- [ ] Убедиться, что `.env` с ключом модели на месте, сервис отвечает: `/healthz`.
- [ ] Положить рядом файлы для загрузки: эталонный `.xlsx`, «битый» `.xlsx`, `.docx`.
- [ ] **Запустить в фоне `python benchmark/run_all.py`** — к Акту 7 отчёт будет готов.

> Раскладка экрана: слева — браузер (UI), справа — терминал/проводник. Демонстрацию ведёт
> один человек (или двое: «рассказчик» + «оператор»).

---

## Акт 1 — Загрузка и устойчивость (Ф-1, Ф-3) — ~5 мин

**Показываем:** система принимает сложные Excel и отбраковывает мусор.

| Действие | Пункт ПМИ | Что проговорить |
|---|---|---|
| Загрузить `data_proportional_prices.xlsx`, открыть список листов | Ф-1 (А-1) | «Файл зарегистрирован, все листы распознаны» |
| Загрузить тот же файл повторно | Ф-1 (А-1) | «Дубль не создан — дедупликация по содержимому» |
| Показать хэш файла до/после (в UI карточки файла) | Ф-1 | «Исходники не изменяются — система только читает» |
| Загрузить `.docx` и повреждённый `.xlsx` | Ф-1 (А-2) | «Недопустимые файлы отклоняются с понятным сообщением» |
| Загрузить Faked-книгу (сложный макет), открыть колонки листа | Ф-3 (А-4) | «Многострочные шапки, объединённые ячейки — разобраны» |
| Загрузить её повторно, показать в трейсе переиспользование разбора | Ф-3 | «Шаблон узнан — разбор переиспользован» |

**Фиксация:** скриншот списка файлов + карточка дубликата; хэши.

---

## Акт 2 — Вопрос и ответ (Ф-2, Ф-5, Ф-7) — ~7 мин

**Показываем:** главный сценарий — вопрос обычным языком, верный ответ с источником.

| Действие | Пункт ПМИ | Что проговорить |
|---|---|---|
| Вопрос по заранее выбранному файлу/листу | Ф-2 (А-3) | «Ответ построен по выбранным данным» |
| Тот же вопрос **без** выбора файла | Ф-2 | «Листы определены автоматически, см. источники в ответе» |
| Вопрос про медный лом на листе с итогами | Ф-7 (А-8) | «SQL исключает строки ИТОГО/ВСЕГО, единица руб/тн указана» |
| Запустить `python benchmark/run_first5.py` в терминале (быстро, кэш разогрет) | Ф-5 (А-6) | «5 задач заказчика — 5 из 5 совпало с эталоном, PASS RATE 100 %» |
| Показать свежий отчёт `benchmark/results/run_first5_*.txt` | Ф-5 | «Каждое значение сверено с эталоном заказчика» |

**Страховка:** если живой прогон Ф-5 подвисает — сразу показываем сохранённый отчёт
от T-1 (факты идентичны), а живой вопрос показываем в UI параллельно.

---

## Акт 3 — Прозрачность: SQL, трейсы, журнал (Ф-6, Ф-9, Ф-12) — ~6 мин

**Показываем:** каждая цифра проверяема — это главная «фишка» для комиссии.

| Действие | Пункт ПМИ | Что проговорить |
|---|---|---|
| В чате по ответу А-6 открыть SQL-блок | Ф-9 (А-10) | «Виден сам запрос к витрине» |
| Открыть трассу `/trace?request_id=…` | Ф-9 | «classifier → planner → codegen → executor → verifier → answer, с длительностями» |
| В трейсе показать выполненный SQL | Ф-6 (А-7) | «Вычисления только через SQL, только чтение» |
| Прогнать `python -m pytest tests/test_codegen_helpers.py tests/test_agent_helpers.py -q` | Ф-6 | «Некорректный SQL отклоняется до выполнения; self-correction до 3 попыток» |
| Открыть `/metrics` (журнал запросов) | Ф-12 (А-12) | «Токены, латентность, статус, версия промптов — всё в журнале» |

## Акт 4 — Графики и выводы (Ф-10, Ф-11) — ~4 мин

| Действие | Пункт ПМИ | Что проговорить |
|---|---|---|
| «Построй линейный график динамики цены … по месяцам» | Ф-10 (А-11) | «График по запросу текстом» |
| «Построй столбчатую диаграмму … по поставщикам» | Ф-10 | «Другой тип визуализации по той же витрине» |
| Нажать кнопку «Сделай график» под табличным ответом | Ф-10 | «И по кнопке — без текста» |
| Прочитать текстовый вывод агента (тренд/лидеры) | Ф-11 (А-11) | «Вывод не противоречит цифрам: min/max на графике видны» |

## Акт 5 — Диалог и надёжность (Ф-8, Ф-13) — ~4 мин

| Действие | Пункт ПМИ | Что проговорить |
|---|---|---|
| Вопрос без периода: «Какая цена у поставщика …?» | Ф-8 (А-9) | «Система переспросит, а не будет угадывать: waiting_for_input» |
| Показать историю диалога с уточнением | Ф-9 | «Диалог сохраняется» |
| Задать многошаговый cross-sheet вопрос | Ф-13 (А-13) | «Ход выполнения виден (AgentProgress), интерфейс не блокируется» |

---

## Акт 6 — Конфигурация без правки кода (Ф-4) — ~2 мин

**Вариант А (живьём):** показать `.env`, изменить имя модели, `docker compose restart service`,
задать короткий вопрос (кэш-код), показать в трейсе новую модель, `git status` — чисто.

**Вариант Б (страховка):** заранее подготовленные скриншоты «до/после» + вывод `git status`.
Если время демонстрации жмёт — используем вариант Б и оговариваем это.

---

## Акт 7 — Метрики качества (К-1, К-2, К-3) — ~4 мин

| Действие | Пункт ПМИ | Что проговорить |
|---|---|---|
| Показать отчёт `benchmark/results/run_all_*.json` (фоновый прогон из T-0) | К-1 (А-16) | «PASS RATE ≥ 80 %» |
| Разобрать JSON по типам (lookup / max-min / агрегат / дельта / cross-sheet) | К-2 | «По каждому типу ≥ 80 %» |
| Сопоставить с результатами связок Заказчика | К-3 | «Не ниже 60 % от результата связок» |

> Если фоновый прогон успел — показываем «свежий живой», иначе заранее зафиксированный.

## Риски и запасные варианты

| Риск | Вероятность | Запасной план |
|---|---|---|
| LLM-таймаут / флап модели на живом вопросе | средняя | повторный вопрос (кэш), затем скриншоты T-1 |
| Живой `run_all` не успевает за 30 мин | высокая | отчёт, прогнанный заранее (T-1) |
| Docker/сервис упал | низкая | снапшот стенда; перезапуск `docker compose up -d` |
| Комиссия торопит | средняя | Акты 1, 2, 4, 7 — минимальный маршрут (~15 мин); остальные — «по протоколу, зафиксировано в приложении» |
| Вопрос из зала «а покажите…» | высокая | инкогнито-вкладка с чистой сессией + папка скриншотов `pmi/` |

**Минимальный маршрут (если дали 15 минут):** Акт 2 → Акт 3 (трейс + SQL) → Акт 4 → Акт 7.
Остальные пункты закрываются скриншотами/отчётами из приложения к протоколу.
