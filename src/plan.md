# EVRAZ Agent — План улучшений

> Полный план развития проекта «вопрос-ответ по Excel-файлам с ценами на цветной лом».
> Базируется на анализе реальных данных (`data/`) и примеров запросов (`docs/request_examples.txt`).

---

## 0. Контекст и текущие боли

**Реальные данные (`data/data_proportional_prices.xlsx`):**
- 12 листов по месяцам 2025 (`цв.лом(на дек25)` … `цв.лом(на янв25)`), формат A1:R81.
- Многоуровневая шапка (3 строки): верхний уровень «по результатам аукциона», средний — поставщики, нижний — подколонки аукциона.
- Много пустых ячеек (у части поставщиков по отдельным позициям нет цен).
- Есть готовая колонка «Среднерыночная цена» (уже посчитанное среднее) + отдельные колонки поставщиков.

**Второй файл (`Faked_List_proportional (2).xlsx`) — другой формат:**
- Листы «2 блок» (200×67), «3 блок» (264×146), «Отклонения от БЮДЖЕТА и ПЛАНА» (84×34).
- Совсем иная структура: проценты состава шихты, планы/факты, отклонения. Не цены за лом.

**Запросы (`docs/request_examples.txt`) — 5 групп:**
1. Простой поиск значения на одном листе (цена по лому, месяцу, поставщику).
2. Сравнение по нескольким листам (максимум/минимум за год).
3. Средние по нескольким позициям/поставщикам.
4. Дельта/разница (между поставщиками, месяцами, стартом и победителем).
5. Сложные условия (суммы, фильтры, поиск конкретной цены во всех месяцах).

**Текущие проблемы в архитектуре:**
- Модель `mart.price_facts` заточена под «цена лома по месяцу» и плохо покроет второй формат (шихта/план/факт/отклонение).
- Нормализация полагается на жёсткие индексы колонок (`col_index == 2` для наименования), что ломается на разных структурах.
- Нет нормального маппинга поставщиков (алиасы, синонимы), нет поддержки «среднерыночная vs поставщик».
- Агент генерирует SQL напрямую по `mart.price_facts`; нет памяти диалога, нет контекста файлов, слабая обработка пустых ячеек (NULL) в расчётах.
- Промпты — хардкод строк, нет версионирования/шаблонизации.
- Фронтенд уже на React+TS, но его требуется полностью переработать (структура, дизайн, UX, состояние).

## 1. Парсинг и нормализация Excel

### 1.1 Универсальный конвейер «лист → факты»
**Проблема:** два формата сильно различаются. `mart.price_facts` рассчитана на «цена лома».
**Решение:**
- Ввести **типизацию листов** (`sheet_kind`): `prices` (цены лома) / `matrix` (шихта-план-факт) / `generic`.
- Сделать **detector** формата: по шапке, именам листов, наличию ключевых слов («цена», «руб./тн», «аукцион», «план», «факт», «отклонение»).
- Разделить нормализацию на **семантические извлечения**:
  - `PriceExtractor` — для `prices` (нынешняя логика, но с dynamic-заголовками).
  - `MatrixExtractor` — для `matrix` (план/факт/отклонение/проценты), кладёт в новую таблицу `mart.metrics`.
  - `GenericExtractor` — fallback (сырые `raw.cells`).

**Модель:**
- Расширить `mart.price_facts` (оставить) и добавить **`mart.metrics`**:
  `(id, file_id, sheet_id, source_row_ref, dimension_type, dimension, period, metric_type, metric, value, unit)` — универсальная long-таблица для любых числовых таблиц (план/факт/процент/отклонение).

### 1.2 Динамические заголовки вместо жёстких индексов
**Проблема:** `normalizer.py` использует `col_index == 2` для наименования и `col_index <= 4` для цен.
**Решение:**
- Парсить шапку в **дерево заголовков** (уже есть `TableStructurer`), но искать семантическую роль по **колонке**:
  `наименование/материал/лом` → item; `цена/руб` → price; `поставщик` → supplier; `%` → percent; `план/факт/отклонение` → metric_type.
- Хранить маппинг `col_role` в `column_metadata` (добавить колонку `role`).

### 1.3 Маппинг поставщиков и сущностей
**Проблема:** «северо-запад ВторМет * (921)341-19-36 (Алла)» vs «Северо-запад», «ЦветМет» — синонимы.
**Решение:**
- Добавить таблицу **`mart.supplier_aliases`** (`canonical_name`, `alias`) + заполнять из шапки.
- Расширить `entity_dictionary` на **supplier/period** (сейчас только item).
- Нормализация единиц/валют (`руб/тн` → `value` + `unit='тн'`, `currency='RUB'`).

### 1.4 Обработка пустых ячеек и типов
- Сохранять признак «пусто» явно (`value IS NULL`), не превращать в 0.
- В `price_facts` хранить `is_blank` флаг, чтобы SQL-агент корректно считал средние (делить на заполненные).

## 2. Схема данных и миграции

**План миграций (новые Alembic):**
1. `add_mart_metrics` — создать `mart.metrics`.
2. `add_column_role` — `column_metadata.role`.
3. `add_supplier_aliases` — `mart.supplier_aliases`.
4. `add_sheet_kind` — `sheets.sheet_kind` + `sheets.semantic_kind`.

**Модели ORM:** `Metric`, `SupplierAlias`, поля `Sheet.sheet_kind`, `ColumnMetadata.role`.

## 3. SQL-генерация и поиск данных

### 3.1 Расширенный генератор SQL
- Генератор должен знать **обе** таблицы (`mart.price_facts` и `mart.metrics`) и выбирать нужную по `sheet_kind`/типу вопроса.
- Поддержка выражений, которые сейчас ломаются:
  - `AVG(...) FILTER (WHERE value IS NOT NULL)` — среднее по заполненным.
  - `MAX/MIN` по периодам (JOIN по item_name между месяцами).
  - Дельта между колонками поставщиков / между стартом и победителем.
  - `ILIKE` с нормализацией пробелов/знаков.

### 3.2 Черновик-каталог «вопрос → шаблон SQL»
- Собрать **few-shot** из `docs/request_examples.txt` (20 примеров) в структурированный файл `tests/golden_questions.json` уже расширить на все группы.
- Добавить **типы запросов**: `lookup`, `aggregate`, `cross_sheet`, `delta`, `sum_by_supplier`, `find_period`.

### 3.3 Надёжный executor
- Усилить keyword-blacklist и добавить **проверку схемы** (только `mart.*`, никаких `raw.cells`/`information_schema`).
- `LIMIT` по умолчанию, таймаут уже есть.
- **Пост-обработка пустых ячеек**: помечать `null` в ответе, чтобы агент не выдавал 0.

## 4. Улучшение агента

### 4.1 Память и состояние (диалог)
- Добавить **conversation context** (хранить историю вопросов/ответов в сессии).
- Ввести `conversation_id` в API `/ask`, сохранять историю в `query_logs`/новой таблице `conversations`.
- Передавать последние 3-5 оборотов в Classifier/Planner (учёт уточнений: «а в декабре?»).

### 4.2 Двухэтапная маршрутизация
- **Router/Classifier** сначала определяет **домен** (`prices` / `metrics` / `generic`) и выбирает схему + таблицу.
- Затем узел `EntityResolution` ищет сущности (item/supplier/period) через pg_trgm.

### 4.3 Верификатор с учётом семантики
- Обучить Verifier сверять ответ с `sql_result`, учитывая NULL-ячейки и единицы измерения.
- Добавить **самопроверку SQL** перед выполнением: «выполняется ли запрос к правильной таблице и колонкам».

### 4.4 Промпты → шаблоны
- Вынести все системные промпты в отдельный модуль/папку (`src/prompts/*.md`), версионировать.
- Добавить **псевдосхему** в промпт: пример данных и колонок, чтобы LLM не выдумывал значения.

### 4.5 Инструменты-функции (Tool calling)
- Вместо «сгенерируй SQL текстом» — **структурированный JSON** (`table`, `columns`, `filters`, `aggregation`) → детерминированный компилятор SQL. Это резко повысит надёжность.

### 4.6 Кэш и повторное использование
- Усилить `query_cache`: нормализация вопроса (синонимы: «медь»/«Медь», «дек»/«декабрь»), хэш → готовый SQL/результат.

- **Дизайн-система**: Tailwind CSS + shadcn/ui (компоненты) или MUI. Тёмная тема под «металлургию».

### 6.2 Структура папок (рекомендация)
```
frontend/src/
  app/            # провайдеры, router, тема
  features/
    chat/         # чат-модуль (UI, поток, типизация, вложения)
```

### 6.3 Ключевые улучшения UX
- **Чат**: streaming-ответы (SSE), отображение шагов агента (progress stepper), markdown, таблицы результатов, кнопка «показать SQL/источник», экспорт в CSV.

- **Dashboard**: сводка по файлам, топ-запросы, латентность, ошибки (из `/metrics` + query_logs).
- **Trace**: таймлайн узлов с latency, SQL preview, diff между попытками retry.
- **Settings**: конфигурация LLM, ключи, rate-limits.

### 6.4 Типизация
- Сгенерировать типы из Pydantic-схем (OpenAPI → TS через `openapi-typescript`) — единый контракт `src/shared/api`.

## 9. Риски и решения

| Риск | Митигация |
|------|-----------|
| Новые форматы Excel | Детектор + `generic` fallback + ручное подтверждение схемы |
| Пустые ячейки искажают средние | `is_blank` флаг + `FILTER (WHERE ... IS NOT NULL)` |
| LLM выдумывает поставщиков/значения | Строгий entity-resolution + few-shot + компилятор SQL |
| SQL к не той таблице | Проверка схемы `mart.*` + маршрутизация по домену |
| Масштаб переделки фронта | Поэтапно: сначала каркас + чат, затем остальное |
