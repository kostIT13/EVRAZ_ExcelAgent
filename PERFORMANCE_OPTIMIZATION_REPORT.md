# Отчёт об оптимизации производительности загрузки/индексации файлов

Дата: 2026-08-06
Область: пайплайн `POST /files/upload → process_file → build_index_for_file`

## Итог

Устранены узкие места, которые в сумме приводили к десяткам минут обработки одного
Excel-файла. Главный источник тормозов — **`EntityResolver`** (резолвинг названий лома)
— полностью переработан: справочник загружается один раз и сравнивается через C-реализацию
`rapidfuzz` вместо чистого Python-Levenshtein. Дополнительно убраны N+1 запросы и
включён bulk-insert ячеек.

---

## 1. `src/services/rag/entity_resolver.py` — главное узкое место

### Проблема
- Для каждого уникального названия лома `_find_entity` выполнял **два полных
  `SELECT * FROM entity_dictionary`** (поиск по алиасам и fuzzy-match), полностью
  последовательно через `await` в цикле, без кэша списка сущностей.
- Fuzzy-сравнение шло через чистый Python-Levenshtein против **каждой** сущности и
  **каждого** алиаса — сложность `O(имён × размер_справочника)`.

### Что сделано
1. **Загрузка справочника один раз** — добавлен метод `_load_all_entities()` с TTL-кэшем
   (`DICT_CACHE_TTL_SECONDS = 300`). `resolve_batch` и `resolve` теперь читают
   `entity_dictionary` один раз и переиспользуют список в памяти, а не выполняют
   `SELECT *` на каждое имя.
2. **Fuzzy через `rapidfuzz`** — метод `_fuzzy_best()` использует
   `rapidfuzz.process.extractOne(..., scorer=fuzz.ratio)` (C-реализация), которая на
   порядки быстрее Python-Levenshtein.
3. **`_find_entity` стал синхронным** над списком в памяти:
   точное совпадение → точное по алиасам → fuzzy по каноническим именам → fuzzy по алиасам.
   Никаких запросов к БД внутри.
4. **Каноническое имя из кэша** — закешированные ID больше не требуют отдельного
   `SELECT` по `id`; имя берётся из уже загруженного справочника через `_entity_by_id()`.

### Эффект
Сложность резолвинга снижена с `O(имён × 2 × SELECT *)` + `O(имён × справочник × Python)`
до **одного** `SELECT *` + `O(имён × справочник)` в C-коде rapidfuzz. При сотнях
уникальных позиций и растущем справочнике — ускорение на порядки.

## 2. `src/services/rag/rag_service.py` — N+1 в `_build_sheet_text`

### Проблема
В fallback-ветке (без fact-строк) для каждой из до 500 строк листа выполнялся
отдельный `SELECT` ячеек этой строки — классический **N+1** паттерн.

### Что сделано
Вместо цикла с отдельными запросами по строкам теперь **один** `SELECT` всех ячеек
листа (в пределах лимита), сгруппированный по `row_num` в Python (`cells_by_row`).

### Эффект
`O(1)` запрос вместо `O(500)` запросов в худшем случае.

---

## 3. `src/services/excel/repository.py` — bulk-insert ячеек

### Проблема
Каждая ячейка добавлялась через `session.add(Cell(...))` — при тысячах ячеек это
тысячи отдельных ORM-операций.

### Что сделано
Ячейки собираются в список словарей и вставляются одним
`session.execute(insert(Cell), cell_rows)` на лист.

### Эффект
Вставка ячеек ускоряется в разы для листов с большим числом ячеек.

## 4. `pyproject.toml` — новая зависимость

Добавлена `rapidfuzz>=3.14.5` (уже присутствует в окружении, версия 3.14.5),
используется для fuzzy-матчинга сущностей.

## 5. Эмбеддинги на CPU — `src/core/config.py`, `src/services/rag/embedder.py`, `src/services/llm/llm_client.py`

### Диагностика из логов Ollama
Из реальных логов работающего приложения видно **доминирующий** источник времени
индексации — инференс эмбеддингов на CPU:

```
[GIN] ... | 200 | 39.829563137s | POST "/v1/embeddings"
output_reserve: reallocating output buffer from size 0.96 MiB to 356.22 MiB
output_reserve: reallocating output buffer from size 408.89 MiB to 2191.92 MiB
```

Один батч эмбеддингов занимает **~40 секунд**, а Ollama многократно раздувает буфер
`output_reserve` с ~1 MiB до ~2 ГБ. Причина: батч из 32 длинных текстов (до 6000
символов каждый) на CPU даёт гигантский батч в токенах и дорогие переаллокации.

### Что сделано
1. **`EMBED_BATCH_SIZE` стал настраиваемым** через конфиг (`settings.EMBED_BATCH_SIZE`,
   дефолт **8** вместо 32). Для последовательного CPU-инференса меньший батч даёт
   меньше переаллокаций буфера Ollama и лучшее время одного запроса. Значение можно
   переопределить через `.env` (например `EMBED_BATCH_SIZE=16`), подобрав под окружение.
2. **Логирование времени батча** в `LLMClient.embed_batch` — теперь в логах приложения
   видно, сколько секунд занимает каждый батч и сколько символов в нём. Это позволит
   точно понять, где основное время, и подобрать оптимальный батч/модель.

### Ограничение
Сама скорость `bge-m3` на CPU — аппаратное ограничение, которое кодом не обойти
полностью. Батчинг снижает число round-trip'ов и переаллокаций, но для радикального
ускорения нужен GPU либо более лёгкая embedding-модель.

## Что сознательно НЕ менялось и почему

| Предложение | Статус | Причина |
|---|---|---|
| `load_workbook(read_only=True)` в парсере | Не менялось | `parser._unmerge_cells` **записывает** значения в workbook, а `read_only` несовместим с записью. Потребовало бы переписывания логики разъединения ячеек. |
| Перенос fuzzy в Postgres `pg_trgm` | Не менялось | Требует установки расширения и GIN-индексов (миграция БД). Быстрее всего реализовать в памяти через rapidfuzz, что и сделано. |
| Асинхронный upload (202 + BackgroundTasks/очередь) | Не менялось | Архитектурное изменение, требующее поллинга статуса и обработки фоновых задач; отдельная задача. |
| Параллельная индексация листов через `asyncio.gather` | Не менялось | Зависит от параллельности Ollama (`OLLAMA_NUM_PARALLEL`); отдельная задача с проверкой окружения. |

## Рекомендуемые следующие шаги (вне скоупа данной задачи)

1. **Асинхронный upload**: `POST /files/upload` возвращает `202` + `file_id`, обработка
   уходит в фон (FastAPI `BackgroundTasks` или очередь Celery/arq), клиент поллит
   `GET /files/{id}` (поле `status` уже есть).
2. **Подобрать `EMBED_BATCH_SIZE`** под окружение (сейчас по умолчанию 8). Ориентир —
   логи `Embedded batch: ... took=...s` из нового логирования. Если время батча всё ещё
   велико, уменьшить батч или перейти на GPU/лёгкую embedding-модель.
3. **`pg_trgm` + GIN-индекс** на `entity_dictionary.canonical_name` для переноса
   fuzzy-match в SQL при очень большом справочнике.
4. **Параллельная индексация листов** через `asyncio.gather` при включённом
   `OLLAMA_NUM_PARALLEL`.
