# AI-агент для работы с Excel (ЕВРАЗ-1)

Система, отвечающая на вопросы по Excel-файлам с полным объяснением источника ответа (traceability), без утечки коммерческой тайны (цены на металлы) наружу.

---

## 1. Цели и ограничения

**Цель:** точность ≥85% на 5 типах запросов из демо ЕВРАЗа, с полным traceability ответа.

**Жёсткие ограничения:**
- Данные — коммерческая тайна (цены на металлы). Сырые цифры наружу не уходят.
- Файлы — «грязные»: multi-level headers, merged cells, разные структуры листов.
- Ответ должен быть traceable: пользователь видит, из какой ячейки взят результат.
- Latency ≤ 15 сек на типичный запрос, ≤ 60 сек на сложный cross-sheet.

**Не-цели MVP:**
- Работа с макросами (.xlsm) — откладываем.
- Real-time коллаборация.
- Мобильный клиент.

---

## 2. Архитектура (слои)

1. **Ingestion** — парсинг Excel → нормализация → загрузка в Postgres.
2. **Retrieval** — гибридный поиск релевантных листов/колонок (keyword + pgvector + metadata).
3. **Agent Orchestrator** — state machine: Classifier → Planner → CodeGen → Validator → Executor → Verifier.
4. **Sandbox** — изолированное исполнение SQL/кода в Docker.
5. **Traceability** — маппинг результата на конкретные ячейки, полный trace запроса.
6. **API** — FastAPI, endpoints `upload` / `ask` / `trace/{request_id}`.

---

## 3. Этапы реализации

### Этап 1: MVP (6 недель)
Работает на 5 типах запросов из демо, только на «чистых» файлах.

**Deliverables:**
- Ingestion pipeline: парсинг → нормализация → загрузка в Postgres.
- Базовый retrieval: keyword search по названиям листов/колонок.
- SQL-based code generation с pre-execution валидацией.
- Docker-sandbox.
- FastAPI с endpoints `upload`/`ask`.
- Бенчмарк на 30 кейсах (6 на каждый тип запроса).
- Traceability: ответ + список использованных листов/ячеек.

**Критерий готовности:** ≥75% accuracy на бенчмарке, latency p95 ≤ 20 сек.

### Этап 2: V1 (4 недели)
Работа с «грязными» файлами и сложными запросами.

**Deliverables:**
- Merged cells classifier + multi-level header resolver.
- Гибридный retrieval (keyword + pgvector + metadata filters).
- LLM-классификатор типа запроса.
- Кэш ответов (Redis).
- Audit log + feedback loop.
- Расширение бенчмарка до 100 кейсов, включая edge cases.
- UI для traceability (показать путь от вопроса к ячейке).

**Критерий готовности:** ≥85% accuracy на бенчмарке, в т.ч. ≥80% на cross-sheet.

### Этап 3: V2 (4 недели)
Продакшен-готовность.

**Deliverables:**
- Incremental re-upload с версионированием.
- Защита от prompt injection.
- Обработка больших файлов (streaming, лимиты).
- Мониторинг (Prometheus + Grafana на своих метриках).
- A/B тестирование разных LLM-стратегий.
- Документация + onboarding для пользователей.

## 4. Детализация критических модулей

### 4.1. Ingestion Pipeline
Цель: превратить любой Excel в нормализованную схему без потери семантики.

- **Структурный парсинг** (openpyxl) + классификатор merged cells (лёгкая LLM, Ollama Llama 3.1 8B, точность ≥90% для MVP).
- **Нормализация:** каждый лист → DataFrame с единой строкой заголовков; названия колонок → snake_case + маппинг на оригинал; типы данных определяются (date/number/currency/text); пустые строки/столбцы удаляются с логированием.
- **Загрузка в Postgres** по схеме `sheets` / `columns` / `cells`.
- **Семантические описания** (Ollama локально): для каждого листа и колонки генерируется краткое описание → эмбеддинги → pgvector.
- **Лимиты:** 50 МБ на файл, 100 листов, 1М ячеек; парсинг батчами по 10 листов.

### 4.2. Retrieval (гибридный поиск)
Keyword + pgvector + metadata filters. Важно: чисто числовые запросы («где минимальная цена») плохо ловятся эмбеддингами — keyword/metadata обязательны как fallback.

### 4.3. Agent Orchestrator (state machine)
Простой Python state machine вместо LangGraph (для MVP избыточен, миграция потом ~2 дня).

Цепочка: **Classifier → Planner → CodeGen → Validator → Executor → Verifier**

- **Classifier (LLM, API):** вопрос + список названий листов → `query_type` (lookup/aggregate/cross_sheet/delta) + сущности.
- **Planner (LLM, API):** вопрос + схема релевантных листов → текстовый план. В план передаётся только схема, не сырые данные.
- **CodeGen (LLM, API):** план + схема Postgres → SQL-запрос (без `SELECT *`).
- **Validator (код, без LLM):** проверка SQL перед исполнением.
- **Executor (Docker-sandbox):** исполнение запроса в изоляции.
- **Verifier (LLM, API):** проверка, отвечает ли результат на вопрос; если нет и retry_count < 3 → назад в CodeGen с уточнением.

### 4.4. Sandbox (Docker per request)
Docker вместо RestrictedPython (последний тривиально обходится).

- Base image: `python:3.11-slim` + pandas, numpy, psycopg2.
- `network_mode="none"`, `read_only=True` (кроме `/tmp`).
- `mem_limit="512m"`, `cpu_quota=50000`, `pids_limit=64`.
- `security_opt=["no-new-privileges"]`, non-root user.
- Таймаут 30 сек.
- Whitelist библиотек: pandas, numpy, datetime, json.
- Логи stdout/stderr → таблица `execution_logs`.

### 4.5. Traceability
Каждый шаг агента пишет в trace; результат SQL маппится на конкретные ячейки. Endpoint `GET /trace/{request_id}` возвращает полный путь: вопрос → план → SQL → результат → источник (лист + ячейка).

### 4.6. LLM Strategy (API vs Ollama)

| | Используется для |
|---|---|
| **Ollama (локально)** | Всё, что касается сырых данных: суммаризация листов при ingestion, классификация merged cells, fallback при недоступности API |
| **API (GPT-4o / Claude)** | Только абстрактные задачи без сырых данных: Classifier, Planner, CodeGen, Verifier (результат — агрегированный) |

- **Fallback:** если API недоступно > 30 сек → переключение на Ollama (Llama 3.1 70B при наличии GPU, иначе 8B).
- **Кэш:** Redis, ключ `hash(question + file_id)`, TTL 1 час, инвалидация при re-upload файла.

### 4.7. Безопасность
- Санитизация всех строк из Excel перед отправкой в LLM (защита от prompt injection).
- Чёткое разделение в промптах: данные из файла vs вопрос пользователя, с инструкцией игнорировать команды внутри данных.
- Audit log: `request_id, user, question, plan, sql, result, latency_ms, created_at`, retention 1 год, доступ только через админский API.

## 5. Стек технологий

| Слой | Технология | Почему |
|---|---|---|
| API | FastAPI | Быстрый, асинхронный, автодокументация |
| БД | PostgreSQL 15 | Надёжность, pgvector встроен, JSONB для метаданных |
| Векторный поиск | pgvector | Не плодим сущности, для 100–1000 листов достаточно |
| Кэш | Redis | Простой, быстрый, TTL из коробки |
| Оркестрация | Python state machine | Проще LangGraph для MVP, миграция легка |
| LLM (локально) | Ollama + Llama 3.1 8B/70B | Данные не уходят наружу |
| LLM (API) | GPT-4o / Claude 3.5 | Качество для сложного planning |
| Excel-парсинг | openpyxl + pandas | openpyxl для merged cells, pandas для нормализации |
| Sandbox | Docker | Изоляция, лимиты ресурсов |
| SQL-валидация | sqlparse | Лёгкий, без исполнения |
| Тестирование | pytest + свой бенчмарк | Регрессия по типам запросов |
| Мониторинг (V2) | Prometheus + Grafana | Свои метрики, без внешних зависимостей |

## 6. Метрики и бенчмарк

**Бенчмарк (100 кейсов):**
- Single-sheet lookup — 20
- Multi-sheet max/min — 20
- Group-by агрегаты — 20
- Delta (разница во времени) — 20
- Cross-sheet сравнение — 20
- Edge cases (доп. 20): пустые листы, файлы с 50+ листами, exploratory-вопросы, некорректные вопросы

**Метрики:**
- Accuracy по каждой категории отдельно (не усреднённо).
- Latency: p50/p95/p99.
- Cost: токены на запрос (API).
- Fallback rate: % запросов, ушедших в retry.
- Traceability coverage: цель 100%.

**Целевые значения (V1):** Accuracy ≥85% overall, ≥80% по каждой категории; latency p95 ≤15 сек; fallback rate ≤10%.

## 7. Риски и митигации

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Merged cells classifier ошибается | Высокая | Средняя | Собрать 50+ примеров от пользователей, дообучить |
| LLM генерирует невалидный SQL | Средняя | Средняя | Pre-execution валидация + retry (до 3 раз) |
| Эмбеддинги не работают для числовых запросов | Высокая | Высокая | Гибридный retrieval (keyword + metadata обязательны) |
| Большие файлы роняют ingestion | Средняя | Высокая | Лимиты + streaming-парсинг + отказ с объяснением |
| Prompt injection через Excel | Низкая | Высокая | Санитизация + разделение данных/инструкций |
| API LLM недоступно | Средняя | Средняя | Fallback на Ollama |
| Пользователи не доверяют ответам | Высокая | Высокая | Traceability + UI с показом источника |

## 8. Команда и таймлайн

**Команда (минимум):**
- 1 Backend-разработчик (ingestion, API, БД)
- 1 ML-инженер (LLM-интеграция, retrieval, бенчмарк)
- 0.5 DevOps (Docker-sandbox, деплой)
- 0.5 Frontend (UI для traceability, V1)
- 0.5 PM/аналитик (сбор бенчмарка, работа с пользователями)

**Таймлайн:**
- Недели 1–2: ingestion pipeline + БД-схема
- Недели 3–4: retrieval + базовый агент (state machine)
- Недели 5–6: sandbox + traceability + бенчмарк (MVP)
- Недели 7–8: гибридный retrieval + LLM-classifier + кэш (V1)
- Недели 9–10: UI для traceability + feedback loop
- Недели 11–12: безопасность + мониторинг + документация (V2)

## 9. Первые 2 недели — что делать в первую очередь

1. Собрать 20–30 «грязных» Excel-файлов от реальных пользователей ЕВРАЗа — без этого ingestion теоретический.
2. Разметить 30 кейсов для бенчмарка (6 на каждый тип запроса).
3. Реализовать ingestion pipeline на этих файлах, отладить merged cells + multi-level headers.
4. Поднять Postgres + pgvector, загрузить нормализованные данные.
5. Написать базовый retrieval (keyword search), проверить, что находит релевантные листы.

**Принцип:** *ingestion > agent*. Если данные нормально не распарсили — никакой агент не спасёт.

## 10. Дополнения: чего не хватает для production-ready

Ниже — блок, добавленный сверх исходного плана. Всё это стоит закрыть до полноценного прод-релиза (частично можно встроить в V2, частично — отдельный этап V3).

### 10.1. Multi-tenancy и изоляция данных
Если система будет использоваться не только ЕВРАЗом (или разными подразделениями с разным уровнем доступа к ценам), нужна изоляция по `tenant_id`:
- Отдельная схема или RLS (row-level security) в Postgres на уровне `tenant_id`.
- Sandbox-контейнеры не должны иметь доступа к данным чужого тенанта даже теоретически.

### 10.2. RBAC (роли и доступ)
- Роли: кто может грузить файлы, кто может задавать вопросы, кто видит audit log.
- Разграничение на уровне отдельных листов/колонок (например, не все пользователи должны видеть закупочные цены).

### 10.3. Версионирование и diff файлов
План упоминает "incremental re-upload с версионированием" в V2, но не раскрывает механику:
- Хранить историю версий (snapshot или diff) для каждого file_id.
- Возможность спросить "как изменилась цена с прошлой версии" — это естественное расширение delta-запросов.
- Откат к предыдущей версии при ошибке ingestion.

### 10.4. Rate limiting и квоты
- Лимиты на количество запросов/загрузок в единицу времени на пользователя и на tenant.
- Отдельные квоты на LLM API вызовы (защита от случайного/злонамеренного исчерпания бюджета).

### 10.5. Cost control (unit-экономика)
- Бюджет на токены в день/месяц с алертами при аномалиях.
- Метрика "стоимость на правильный ответ" — не только accuracy, но и экономика на кейс.
- Дашборд разбивки расходов по этапам агента (Classifier/Planner/CodeGen/Verifier).

### 10.6. Human-in-the-loop для low-confidence ответов
- Если Verifier не подтвердил ответ после 3 попыток — не молчаливый провал, а явная эскалация: показать пользователю "не уверен" + предложить передать на ревью аналитику.
- Собранные эскалации — источник новых кейсов для бенчмарка.

### 10.7. Graceful degradation
- Чёткое поведение UI/API при: недоступности LLM API, недоступности Ollama, таймауте sandbox, превышении лимитов файла.
- Пользователь должен получать понятное сообщение, а не generic 500.

### 10.8. CI/CD и regression gate
- Бенчмарк должен запускаться в CI на каждый PR/деплой.
- Порог: деплой блокируется, если accuracy по любой категории просела более чем на X% от baseline.
- Отдельный canary/staging контур с реальными (анонимизированными) файлами перед прод-раскаткой.

### 10.9. Backup и disaster recovery
- Backup policy для Postgres (WAL + периодические снапшоты).
- Явные RPO/RTO.
- План восстановления sandbox-инфраструктуры и Redis-кэша (кэш не критичен для DR, но БД — критична).

### 10.10. Naming/семантический словарь по доменным терминам
- Для металлургии полезен собственный словарь синонимов (марки стали, единицы измерения, сокращения), который используется и в retrieval, и в санитизации/классификации — это должно снизить количество ошибок retrieval на этапе V1–V2 без необходимости дообучать модели.

### 10.11. Наблюдаемость (кроме Prometheus/Grafana)
- Трейсинг сквозного запроса (OpenTelemetry) через все этапы agent-конвейера — полезно не только для traceability пользователю, но и для дебага латентности инженерами.
- Алерты на аномальный fallback rate или падение accuracy в проде (не только в бенчмарке).
