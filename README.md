# План проекта: AI-агент для работы с Excel-файлами (ЕВРАЗ-1)
## #1. Суть задачи и главный вызов

Из демо видно, что проблема не в LLM как таковой, а в предобработке табличных данных. Все четыре системы спотыкаются там, где Excel не является "плоской таблицей":

* многоуровневые заголовки (2-3 строки шапки)
* merged cells
* несколько листов с разной структурой
* запросы, требующие агрегации внутри листа vs между листами

Значит, ядро проекта — не "обёртка над LLM", а надёжный слой парсинга + семантическое представление таблицы, поверх которого уже работает агент с function calling / генерацией кода.

## 3. Ключевой модуль: Excel Ingestion Pipeline
Это то, где реально решается bottleneck из демо. Разбивается на подэтапы:
### 3.1. Структурный парсинг

* openpyxl (не pandas.read_excel напрямую) — нужен доступ к merged cells, стилям, комментариям
* Определение "фактической" шапки: эвристика + LLM-classifier для многострочных заголовков
* Разворачивание merged cells (propagate значения вниз/вправо)
* Определение типа листа: data sheet / lookup table / summary / пустой

### 3.2. Нормализация в "плоскую" схему

* Каждый лист → чистый DataFrame с единой строкой заголовков (конкатенация уровней: "Метал | Цена | USD")
* Приведение типов (даты, числа, валюты)
* Явное определение единиц измерения и валюты в метаданных колонки

### 3.3. Семантический слой (для Qdrant)

* Генерация текстового описания каждого листа/колонки (LLM суммаризация: "что это за таблица, какие метрики, диапазон дат")
* Эмбеддинги описаний листов/колонок → Qdrant, для retrieval релевантных таблиц по вопросу
* Это решает multi-sheet routing — агент сначала находит какие листы релевантны, а не грузит весь файл в контекст

### 3.4. Хранение

* PostgreSQL: сырые нормализованные данные (таблица sheets, columns, cells/wide-таблицы per file), плюс метаданные файлов и версии
* Qdrant: эмбеддинги схем/описаний для семантического поиска нужного листа/колонки
* Схема должна поддерживать incremental re-upload (файлы с ценами обновляются регулярно)

## 4. Агентная часть (LangGraph)
Судя по демо, узкое место конкурентов — это то, что они пытаются одним подходом закрыть разнотипные запросы. Предлагается роутинг по типу задачи как явный граф, а не полагаться на одну LLM-цепочку:

### Важные узлы:

* Classifier — определяет тип запроса (lookup / aggregate / cross-sheet / delta) и извлекает сущности (какие металлы, * даты, листы)
* Retriever — Qdrant поиск релевантных листов/колонок по эмбеддингу вопроса (решает проблему "какой лист смотреть")
* Code Generator — LLM генерирует pandas или SQL-код по нормализованной схеме (не по сырому Excel!)
* Sandbox Executor — исполнение кода в изолированном окружении (subprocess/ restricted eval, лимиты по времени/памяти)
* Verifier — self-check: LLM сверяет результат с вопросом, при ошибке — retry с уточнением плана (характерно для * LangGraph — циклы с условными рёбрами)

## 5. Выбор LLM: API vs Ollama

* API LLM (сильная модель) — для генерации кода/плана, классификации сложных запросов, верификации ответа
* Ollama (локальная модель) — для:

* дешёвых/частых операций (суммаризация листов при ingestion)
* fallback при недоступности API
* если данные чувствительные (цены на металлы могут быть коммерческой тайной) — держать pipeline ingestion полностью локально, а на внешний API отправлять только абстрактные схемы/вопросы, не сырые цифры


Это стоит явно продумать: что уходит наружу, а что остаётся в периметре.



## 6. Инструменты по слоям
* API: FastAPI — REST для upload/ask/feedback
* ORM/БД: SQLAlchemy + PostgreSQL — нормализованные данные + метаданные
* Векторный поиск: Qdrant — retrieval релевантных листов/колонок
* Оркестрация агента: LangGraph — явный граф с ветвлением по типу запроса и циклами верификации
* LLM-интеграция: LangChain (частично) — обёртки промптов, парсинг структурированного вывода
* Excel-парсинг: openpyxl, pandas — структурный + табличный парсинг
* Исполнение кода: RestrictedPython / subprocess sandbox / Docker-in-Docker — безопасный code execution
* Мониторинг агента: LangSmith / Langfuse (self-hosted) — трейсинг цепочек, дебаг ошибок routing
* Тестирование: pytest + eval-датасет из 5 типов запросов (как в демо) — регресс-тесты по типам сложности


## 7. Метрики оценки (по образцу демо ЕВРАЗ)
Нужен бенчмарк-набор минимум с этими категориями (расширяемый):

* Single-sheet lookup
* Multi-sheet max/min
* Group-by агрегаты внутри листа
* Delta (min/max разница)
* Min/max по нескольким листам

Метрики: accuracy по каждой категории отдельно (не общий средний — как раз видно, что общий средний скрывает провал на одной категории), latency, стоимость токенов на запрос, % запросов, ушедших в fallback/ошибку.
