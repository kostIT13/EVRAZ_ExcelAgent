# Демонстрация контрольных примеров (Приложение А, PMI.docx)

Сценарий демонстрации для вкладки **Demo** фронтенда.
Формат каждого пункта: ссылка на требование, шаги, ожидаемый результат, готовая формулировка для комиссии, статус подготовки.

> Общие предусловия: система развёрнута (`docker compose up -d postgres service frontend`), модель подключена, эталонные файлы загружены (кроме А-1, А-17).
> Адреса: интерфейс `http://localhost:8080`, Swagger `http://localhost:8000/docs`.

## ✅ А-5 — Конфигурация модели без изменения кода (Ф-4, С-3)

**Шаги:**
1. В Swagger выполнить `GET /config` (с API-ключом) → показать текущие значения:
   `{"model": "Qwen3.8-27B", "temperature": 0.1, "timeout_s": 60, ...}`
2. Открыть `.env`, изменить:
   `LLM_TEMPERATURE=0.1` → `0.7`, `REQUEST_TIMEOUT_S=60` → `90`
3. **`docker compose up -d --force-recreate service`** — пересоздание контейнера
   (важно: обычный `restart` НЕ перечитывает `.env`; recreate — читает, при этом
   образ не пересобирается и код не меняется)
4. Снова `GET /config` → значения изменились: `temperature=0.7, timeout_s=90`
5. Задать вопрос в чате → ответ получен (система работает с новыми параметрами)
6. `git status` → изменений в коде нет (`.env` в `.gitignore` и не появляется)

Дополнительно при старте сервиса в логах виден применённый конфиг:
`docker logs evraz_excelagent-service-1 2>&1 | Select-String "LLM config"`
→ `LLM config: model=Qwen3.8-27B, temperature=0.7, timeout=90s, thinking=False`

**Ожидаемый результат:** ответ получен с новыми параметрами; код не изменён; ключ только в `.env`.

**Формулировка для комиссии:**
> «Смотрите: `GET /config` показывает temperature 0.1 и таймаут 60 секунд. Меняю оба значения в `.env` — код не трогаю. Пересоздаю контейнер одной командой — без пересборки образа. Снова `GET /config` — теперь 0.7 и 90. Задаю вопрос — система работает с новыми параметрами. git status чист: конфигурация отделена от кода, ключи в репозитории отсутствуют».

**Замечания по демо:**
- ключ `LLM_API_KEY` при показе `.env` прикрыть/прокрутить;
- модель менять только на существующую на прокси (иначе 404);
- команда пересоздания: `docker compose up -d --force-recreate service`.

**Результат тестирования:** ✅ Пройден (30.10.2026). `GET /config` до: 0.1/60. После правки `.env` и `--force-recreate`: 0.7/90. Вопрос в чате — отвечает. Код не менялся.

## ✅ А-8 — «Все виды медного лома», исключение итогов (Ф-7)

**Шаги:**
1. Задать в чате:
   `Какова была средняя цена на все виды медного лома по данным Ферроком в феврале 2025 года?`
   → Ответ: **696 625,15 руб./тн** (эталон)
2. Открыть трейс → шаг CodeGen → показать SQL:
   ```sql
   SELECT AVG(fp.value) AS средняя_цена
   FROM mart.price_facts fp
   WHERE fp.sheet_period = '2025-02'
     AND fp.supplier ILIKE '%ферроком%'
     AND fp.item_name ILIKE 'Лом меди%'
   ```
   Акцент: **префикс** `Лом меди%` (НЕ `%мед%` — иначе захватываются сплавы)
3. Доказательство исключения итогов:
   ```bash
   docker exec evraz_postgres psql -U user -d postgres -c "SELECT DISTINCT item_name FROM mart.price_facts WHERE item_name ILIKE '%итог%' OR item_name ILIKE '%всего%'"
   ```
   → 0 строк: итоги («ИТОГО»/«ВСЕГО») в витрине отсутствуют, AVG не искажается
4. Единица измерения «руб./тн» — в тексте ответа

**Ожидаемый результат:** значение равно эталонному; SQL исключает ИТОГО/ВСЕГО; единица измерения указана.

**Формулировка для комиссии:**
> «„Все виды медного лома" — я не перечисляю виды. В SQL поиск префиксом „Лом меди": система включает кусок, микс, стружку, но не захватывает медно-никелевые сплавы. Итоговые строки листа в витрине отсутствуют — вот проверка, ноль строк. Итоги не искажают среднее. Обратите внимание: „по данным Ферроком" система сама перевела в фильтр по поставщику. Единица измерения — в ответе».

**Результат тестирования:** ✅ Пройден (30.10.2026). SQL с префиксным фильтром, итогов в витрине нет, эталон совпал.

   ```bash
   docker exec evraz_postgres psql -U user -d postgres -t -A -c "SELECT count(*) FROM mart.price_facts"
   ```
   → 3970 (не изменилось); хэш файла (GET /files → file_hash) не изменился

**Ожидаемый результат:** все запросы отклонены; хэш и число строк не изменились.

**Фактическое поведение:** на деструктивные запросы система отвечает содержимым таблицы/статистикой (3 970 строк) — DELETE/DROP физически не выполняются; на «/etc/passwd» — обычная выборка цен (доступ к ФС отсутствует в принципе).

**Формулировка для комиссии:**
> «Пробую сломать систему: удалить строки, DROP TABLE, прочитать системный файл. Все три атаки не выполнены. Безопасность здесь не на обещаниях нейросети, а на архитектурных ограничениях: генератор жёстко ограничен SELECT, валидация отсекает деструктивные конструкции до выполнения (blacklist ключевых слов, whitelist таблиц), доступ к БД — read-only. Файловая система агенту недоступна в принципе. Доказательство целостности: 3 970 строк — как и было, хэш не изменился».
